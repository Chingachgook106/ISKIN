# RU-001 — Independent Network Architecture Review  
（Независимый обзор сетевой архитектуры）

---

## 1. Executive conclusion（Итоговый вывод）

- **Рекомендуемый класс архитектуры**：**System-level VPN**（принудительное туннелирование + управление маршрутизацией／брандмауэром）  
- **Второй вариант**：**Overlay-network architecture**（виртуальный сетевой интерфейс с полной изоляцией）  
- **Отклонён**：**Proxy-based architecture**（HTTP/SOCKS-прокси）

Причины：

- **System-level VPN** позволяет на уровне ниже приложений принудительно направлять трафик через «защищённый путь»：  
  - DNS и весь трафик можно централизованно контролировать  
  - IPv4/IPv6-маршруты по умолчанию легко направить через VPN  
  - Приложения (Git, VS Code, Terminal) работают без индивидуальных сетевых настроек  
  - «fail-closed» проще реализовать через маршрутизацию + брандмауэр  
  - Естественная точка расширения для будущего подключения Compute Node  

- **Overlay-network** технически мощный, но на одном узле Windows 11 Pro часто сводится к «тому же VPN, но сложнее»：  
  - Реализация и проверка сложнее  
  - Поведение сильно зависит от конкретного решения (ZeroTier, Tailscale и т.д.)  

- **Proxy-based**：  
  - Протоколы вне HTTP/HTTPS (Git, SSH, некоторые службы Windows) легко обходят прокси  
  - DNS и IPv6 сложно контролировать на уровне ОС  
  - Требует настройки каждого приложения, что противоречит требованию «Network Security Layer под прикладным слоем»

## 2. Current-state interpretation（Текущее состояние）

- Узел：EMS-001 / "Baby"（Windows 11 Pro 25H2, Beelink 5800H）  
- Активный интерфейс：только Ethernet（Wi-Fi, Bluetooth отключены）  
- IPv4-only（нет глобального IPv6, нет IPv6 default route）  
- Git, VS Code установлены, HTTPS-подключение к GitHub работает  
- VPN / прокси / оверлей не установлены  

→ Сейчас узел напрямую выходит в интернет без защищённого пути, что противоречит цели RU-001（перемещение между сетями с блокировкой прямого доступа при недоступности защищённого пути）。

## 3. System VPN analysis（Системный VPN）

### 3.1 Обзор

- В Windows 11 Pro встроенный VPN или сторонний клиент создаёт виртуальный интерфейс (TAP) и туннелирует трафик на IP-уровне.  
- Комбинируя таблицу маршрутизации и Windows Firewall, можно добиться поведения：  
  «Интернет-трафик разрешён только при работающем VPN, при отключении VPN — заблокирован».

### 3.2 Граница безопасности

```
Application
    ↓
Operating System
    ↓
VPN Network Interface (TAP) ← здесь принудительно применяется «защищённый путь»
    ↓
Physical Interface
    ↓
Local Network
    ↓
ISP
    ↓
Internet
```

- VPN-интерфейс становится «единственным выходом в интернет» через настройки маршрутизации и брандмауэра.

### 3.3 Защита DNS

- VPN-клиент может использовать DNS сервера VPN, отключая DNS на физическом интерфейсе.  
- Настройки Windows DNS (`netsh interface ip set dns`, групповые политики) позволяют очистить DNS на физическом интерфейсе или оставить только loopback.  
- При отключении VPN DNS становится недоступным — утечки через DNS минимизируются.

**Поведение Windows DNS**（A. Established facts）：

- Windows позволяет задать DNS-серверы для каждого интерфейса, порядок разрешения зависит от метрики и суффиксов.  
- Но приложения, указывающие свой DNS (DoH-клиенты и т.д.), могут обходить системные настройки — это общая проблема для всех архитектур.

### 3.4 Контроль IPv4 / IPv6

- VPN-клиент может включать принудительное туннелирование IPv4 и либо отключать IPv6, либо туннелировать его.  
- Убирая default route на физическом интерфейсе и оставляя его только на VPN-интерфейсе, можно собрать весь IPv4-трафик через VPN.  
- Если IPv6 появится в будущем, его маршруты также можно контролировать через VPN, отключая IPv6 на физическом интерфейсе.

### 3.5 Управление маршрутизацией

- При подключении VPN скрипты или функции клиента автоматически настраивают маршруты.  
- Удаление default route с физического интерфейса и оставление его только на VPN даёт «force tunnelling».  
- При переподключении, перезагрузке или смене сети VPN-клиент перестраивает маршруты для сохранения поведения.

### 3.6 Независимость от приложений

- Git, VS Code, PowerShell, SSH, HTTPS/API-клиенты используют системный сетевой стек и автоматически идут через VPN.  
- Соответствует модели «Network Security Layer под прикладным слоем».

### 3.7 Мобильность

- Домашняя LAN, офисная LAN, публичная сеть, мобильная точка доступа — если везде есть доступ к VPN-серверу, настройки узла не меняются.  
- Соответствует требованию «не зависеть от конкретного ISP / локальной сети / IP / местоположения».

### 3.8 Совместимость с Compute Node

- Compute Node можно подключить к VPN-серверу, и EMS-001 с Compute Node окажутся в одной виртуальной сети.  
- Естественная точка расширения для безопасного канала между ними.

### 3.9 Операционная сложность

- Установка：требуется VPN-клиент, но есть стандартные и OSS-решения (WireGuard, OpenVPN).  
- Настройка：ключевой элемент — проектирование маршрутизации и брандмауэра.  
- Диагностика：`route print`, `ipconfig`, `netsh` и т.д.  
- Воспроизводимость：скрипты или групповые политики позволяют воссоздать среду.

## 4. Proxy analysis（Архитектура на основе прокси）

### 4.1 Обзор

- HTTP/HTTPS/SOCKS-прокси, настройка в приложениях или системных настройках Windows.  
- Но не все приложения и службы следуют этим настройкам.

### 4.2 Граница безопасности

```
Application
    ↓
Proxy-aware Application Layer ← здесь решается, использовать ли «защищённый путь»
    ↓
Operating System
    ↓
Physical Interface
    ↓
Local Network
    ↓
ISP
    ↓
Internet
```

- Приложения, игнорирующие прокси, могут напрямую выходить в интернет.  
- Противоречит требованию «Network Security Layer под прикладным слоем».

### 4.3 Защита DNS

- HTTP-прокси часто разрешают имена на своей стороне, но приложения могут указывать свой DNS и обходить прокси.  
- Полностью предотвратить утечку DNS сложно.

### 4.4 Контроль IPv4 / IPv6

- Прокси работает на прикладном уровне, не управляет IP-маршрутизацией.  
- Приложения, игнорирующие прокси, могут использовать IPv6 напрямую.

### 4.5 Управление маршрутизацией

- Прокси сам по себе не управляет маршрутами. Для «fail-closed» потребуется дополнительно настраивать брандмауэр и маршруты — усложнение.

### 4.6 Независимость от приложений

- Git, VS Code, SSH поддерживают прокси, но не гарантируют, что весь трафик идёт через него.  
- Требует индивидуальных настроек, что противоречит требованиям.

### 4.7 Мобильность

- Зависит от доступности прокси-сервера из разных сетей.  
- В сетях с жёсткими ограничениями прокси может быть заблокирован.

### 4.8 Совместимость с Compute Node

- Можно общаться через прокси, но это прикладной уровень; для низкоуровневого безопасного канала, скорее всего, понадобится VPN/оверлей.

### 4.9 Операционная сложность

- Настройка каждого приложения, риск пропусков и несоответствий.  
- Диагностика сложнее — нужно проверять каждое приложение.

---

## 5. Overlay-network analysis（Оверлейная сеть）

### 5.1 Обзор

- Виртуальные коммутаторы／интерфейсы поверх физической сети (например, ZeroTier, Tailscale).  
- По сути — разновидность VPN с более гибкой топологией.

### 5.2 Граница безопасности

```
Application
    ↓
Operating System
    ↓
Overlay Virtual Interface ← здесь принудительно применяется «защищённый путь»
    ↓
Physical Interface
    ↓
Local Network
    ↓
ISP
    ↓
Internet
```

- Как и VPN, собирает трафик через виртуальный интерфейс.

### 5.3 Защита DNS

- Многие оверлей-решения управляют DNS, но поведение зависит от реализации.

### 5.4 Контроль IPv4 / IPv6

- Виртуальный интерфейс получает адреса, маршрутизация управляется аналогично VPN.  
- Но в пользовательских реализациях (ZeroTier, Tailscale) поведение может отличаться от классического VPN.

### 5.5 Управление маршрутизацией

- Можно сделать оверлей-интерфейс единственным выходом в интернет.  
- Однако некоторые решения по умолчанию оставляют локальный трафик на физическом интерфейсе — нужно аккуратно проектировать «fail-closed».

### 5.6 Независимость от приложений

- Приложения используют системный стек и автоматически идут через оверлей.  
- Соответствует модели «Network Security Layer под прикладным слоем».

### 5.7 Мобильность

- Как и VPN, не зависит от физической сети.

### 5.8 Совместимость с Compute Node

- Хорошо подходит для mesh-сетей нескольких узлов, включая EMS-001 и Compute Node.

### 5.9 Операционная сложность

- Установка и настройка могут быть сложнее VPN.  
- Диагностика требует понимания конкретной реализации.

## 6. Failure-mode analysis（Анализ отказов）

### 6.1 System VPN

- **Запуск без VPN**：трафик блокируется маршрутизацией／брандмауэром, пользователь видит уведомление.  
- **Обрыв VPN**：клиент удаляет маршруты, интернет-трафик блокируется.  
- **Сбой DNS**：если DNS VPN недоступен, разрешение имён падает.  
- **Неожиданное включение IPv6**：если IPv6-маршруты контролируются VPN, утечки нет.  
- **Перезагрузка／смена сети**：автозапуск VPN и перестройка маршрутов сохраняют поведение.

### 6.2 Proxy

- **Прокси недоступен**：приложения, игнорирующие прокси, идут напрямую.  
- **DNS-сбой**：приложения могут использовать свой DNS.  
- **IPv6 включён**：приложения могут обходить прокси через IPv6.  
- **Перезагрузка／смена сети**：настройки прокси сохраняются, но поведение приложений не гарантировано.

### 6.3 Overlay-network

- Аналогично VPN, но с риском автоматического fallback на физический интерфейс в некоторых реализациях.

---

## 7. DNS analysis（DNS）

- **System VPN**：DNS VPN + отключение DNS на физическом интерфейсе → защита сильная.  
- **Proxy**：DNS может обходить прокси → защита слабая.  
- **Overlay**：сильная, но зависит от реализации.

→ Для DNS **System VPN** проще всего проектировать и проверять.

---

## 8. IPv4 / IPv6 analysis（IPv4 / IPv6）

- **System VPN**：маршруты IPv4/IPv6 собираются через VPN, физический интерфейс блокируется.  
- **Proxy**：IP-уровень не контролируется.  
- **Overlay**：контроль возможен, но реализационно-зависимый.

→ Для строгого «fail-closed» по обоим протоколам **System VPN** предпочтительнее.

---

## 9. Mobility analysis（Мобильность）

- **System VPN / Overlay**：не зависят от физической сети, если есть доступ к серверу／оверлей-сети.  
- **Proxy**：зависит от доступности прокси-сервера.

→ **System VPN** и **Overlay** здесь равны.

---

## 10. Compute Node implications（Расширение для Compute Node）

- **System VPN**：Compute Node подключается к VPN-серверу → естественное расширение.  
- **Proxy**：прикладной уровень, для безопасного канала, скорее всего, потребуется VPN/оверлей.  
- **Overlay**：идеально для mesh-сетей нескольких узлов.

→ **System VPN** и **Overlay** выигрывают.

## 12. Adversarial critique（Критика с позиции противника）

**Самый сильный аргумент против System VPN**：

- Ошибки в настройке маршрутизации или сбои VPN-клиента могут привести к тому, что трафик пойдёт через физический интерфейс, а пользователь будет думать, что защищён.  

Конкретные риски：

- Приложения стартуют до подключения VPN и успевают отправить трафик напрямую.  
- При отключении VPN маршруты очищаются не полностью, остаётся default route на физическом интерфейсе.  
- При включении IPv6 VPN-клиент не блокирует IPv6-маршруты.  
- Сброс сети или перезагрузка возвращают маршруты к начальному состоянию.  

→ Поэтому даже с VPN необходимы：

- Тщательное проектирование маршрутизации и брандмауэра  
- Регулярная проверка реального трафика (например, через packet capture)

## 13. Recommendation（Рекомендация）

1. **Предпочтительный класс**：**System-level VPN**  
   - Причины：  
     - Независимость от приложений, «Network Security Layer под прикладным слоем»  
     - Контроль DNS и IPv4/IPv6 на уровне ОС  
     - «fail-closed» через маршрутизацию + брандмауэр  
     - Хорошая интеграция с Windows 11 Pro, удобство проверки  
     - Естественное расширение для Compute Node  

2. **Второй вариант**：**Overlay-network architecture**  
   - Причины：  
     - Похожи на VPN, но сложнее в реализации и проверке для одного узла  
     - Сильны в будущих mesh-сценариях  

3. **Отклонён**：**Proxy-based architecture**  
   - Причины：  
     - Слабый контроль DNS и IPv6  
     - Требует настройки каждого приложения  
     - Не соответствует требованию «Network Security Layer под прикладным слоем»  

4. **Условия, при которых не следует выбирать System VPN**：  
   - Если основная цель — mesh-сеть нескольких разнородных узлов  
   - Если требуется максимальная платформенная независимость (не только Windows)  

5. **Что нужно проверить на EMS-001 перед внедрением**：  
   - Состояние маршрутов до／после подключения VPN (`route print`)  
   - Состояние DNS до／после VPN (`ipconfig /all`, `nslookup`)  
   - Отсутствие трафика через физический интерфейс при отключённом VPN (packet capture)  
   - Поведение при включении IPv6 (маршруты и DNS)  
   - Поведение при перезагрузке и смене сети (автоподключение VPN и маршруты)

## 14. Experimental verification plan（План проверки）

1. **Снять базовые показания**：`ipconfig /all`, `route print`, `netsh interface ipv4 show config`  
2. **Проверить поведение при подключении VPN**：маршруты, DNS, доступ к внешним сайтам  
3. **Проверить поведение при отключении VPN**：блокировка интернет-трафика  
4. **Проверить поведение при включении IPv6**：маршруты IPv6 и DNS  
5. **Проверить перезагрузку и смену сети**：автоподключение VPN и маршруты  
6. **Провести packet capture**：убедиться, что вне VPN трафик не уходит
