# Подтверждаю старт! И да пребудет с нами сила! 🤖🤩

Отлично, старт подтверждён. Ниже — независимый архитектурный отчёт по RU‑001 для узла EMS‑001 (Windows 11 Pro, IPv4‑only, без глобального IPv6), сфокусированный на требовании fail‑closed и на том, что реально можно гарантировать на уровне ОС, DNS и маршрутизации.[^1]

## 1. Исполнительное резюме

Наилучшим классом архитектуры для требования fail‑closed является системный VPN с принудительным туннелированием и блокировкой всего исходящего трафика при отсутствии активного туннеля (kill‑switch на уровне маршрутов/фильтра).  Прокси‑архитектура не обеспечивает системного fail‑closed без глубокой перестройки сетевого стека (и даже тогда остаётся хрупкой на уровне приложений), а оверлей‑сети сами по себе не дают гарантий блокировки прямого выхода в интернет.[^1]

Критически важно: «VPN подключён» ≠ «fail‑closed». Гарантию даёт только комбинация: отсутствие маршрута по умолчанию через физический интерфейс + наличие маршрута по умолчанию через туннель + политика, запрещающая создание/восстановление прямого дефолта при разрыве туннеля.[^1]

## 2. Интерпретация текущего состояния (по базовому снимку)

- Активный интерфейс: Ethernet 4 (192.168.0.102/24), шлюз 192.168.0.1, DNS 8.8.8.8 и 1.1.1.1 (публичные, без шифрования).[^1]
- IPv6: стек включён, но глобальных адресов и маршрута ::/0 нет; только link‑local.[^1]
- Wi‑Fi/Bluetooth: включены, но не подключены (APIPA), потенциальный вектор локальной утечки метаданных (probe‑запросы и т. п.).[^1]
- Вывод инженера базовой линии: «ноль приватности/безопасности на сетевом уровне» — весь трафик и DNS видны провайдеру и публичным резолверам.[^1]

Это именно та точка, где архитектурный слой должен встать ниже приложений и стать единой точкой контроля для Git/VS Code/Terminal.[^1]

## 3. Системный VPN (туннель на уровне ОС)

### Где проходит граница безопасности

Граница — между сетевым стеком ОС и физическим интерфейсом: весь исходящий трафик приложений проходит через виртуальный TAP/TUN‑интерфейс, затем инкапсулируется и уходит через физический интерфейс.[^1]

### Fail‑closed: как реализовать и как проверить

Реализация (архитектурно, без команд):

- При подъёме туннеля: удалить маршрут по умолчанию с физического интерфейса; добавить маршрут по умолчанию через туннельный интерфейс; запретить DHCP/авто‑восстановление дефолта на физическом интерфейсе (или понизить его метрику до нежелательного уровня).[^1]
- При падении туннеля: автоматически удалять маршрут по умолчанию через туннель; не восстанавливать маршрут по умолчанию через физический интерфейс (kill‑switch на уровне маршрутизации).[^1]
- Дополнительно: правила локального файрвола, разрешающие исходящий 443/1194 и т. п. только к endpoint‑ам туннеля, и блокирующие весь остальной интернет при отсутствии туннеля.[^1]

Проверка (эмпирически):

- Сценарий «туннель недоступен при загрузке»: после перезагрузки без подъёма туннеля попытка достичь внешнего HTTPS‑ресурса должна завершаться таймаутом; при этом локальные ресурсы (шлюз, LAN) могут оставаться доступными, если это явно разрешено.[^1]
- Сценарий «разрыв туннеля»: во время активной загрузки файлов разорвать туннель — трафик должен остановиться (не переключиться на прямой маршрут).[^1]
- Контрольные точки: таблица маршрутов (наличие/отсутствие 0.0.0.0/0 на физическом интерфейсе), состояние туннельного интерфейса, логи файрвола/клиента, результаты тестовых запросов к внешним ресурсам.[^1]


### DNS

Ключевые вопросы и ответы (архитектурно):

- Где резолвят приложения: в Windows — через системный стек (DNS Client), который использует активные DNS‑серверы интерфейса.[^1]
- Как избежать утечки: при подъёме туннеля подменять системные DNS на резолверы внутри туннеля (или использовать DoH/DoT, если туннель это не гарантирует), и запрещать исходящий UDP/53 к внешним IP, кроме разрешённых endpoint‑ов.[^1]
- Поведение при разрыве: если туннель падает, DNS‑серверы туннеля становятся недоступны — резольвинг должен перестать работать; важно не допустить автоматического отката к публичным DNS физического интерфейса.[^1]
- Windows‑специфика: Suffix Search List, Smart Multi‑Homed Name Resolution, и приоритеты интерфейсов могут создавать обходные пути; архитектура должна явно контролировать DNS‑политику (например, через групповые политики/профили).[^1]


### IPv4/IPv6

- IPv4: управляется маршрутом по умолчанию через туннель; при правильном kill‑switch прямой IPv4‑выход блокируется.[^1]
- IPv6: сегодня глобального IPv6 нет, но архитектура должна предполагать его появление в другой сети.  Требуется явная политика: либо отключить IPv6 на уровне ОС/интерфейсов, либо обеспечить туннелирование IPv6 и kill‑switch для ::/0 аналогично IPv4.  Без этого возможен обход через IPv6, если сеть начнёт выдавать глобальные адреса.[^1]


### Маршрутизация и исключения

- Решения о маршрутизации принимаются таблицей маршрутизации Windows; туннельный клиент управляет интерфейсом и маршрутами.[^1]
- Split‑tunnel возможен, но противоречит требованию fail‑closed для общего интернета; допустимы исключения только для локальной LAN (если требуется доступ к принтерам/NAS).[^1]
- После переподключения/ребута: клиент должен восстанавливать политику «дефолт только через туннель», иначе возникает опасное состояние с прямым маршрутом.[^1]


### Независимость приложений

Git, VS Code, PowerShell, SSH, HTTPS/API — все работают прозрачно, так как видят обычный сетевой стек; им не нужна индивидуальная настройка.  Это соответствует целевой модели «один слой сетевой безопасности для всех приложений».[^1]

### Операционная сложность

- Установка: клиент VPN + профиль с политикой маршрутов/DNS.[^1]
- Диагностика: статус туннеля, таблица маршрутов, DNS‑конфигурация, логи клиента/файрвола.[^1]
- Зависимости: сторонний клиент/инфраструктура; требуется документация и тесты на fail‑closed.[^1]


## 4. Прокси‑архитектура (системный/прикладной прокси)

### Граница безопасности

Граница смещается на уровень приложений: только те программы, которые явно используют прокси (или системные настройки WinHTTP/WFP‑перехват), идут через защищённый путь; остальной трафик может идти напрямую.[^1]

### Fail‑closed

- Системный HTTP(S)/SOCKS‑прокси в Windows не даёт универсального fail‑closed для всего трафика (многие приложения игнорируют системные настройки, используют собственные стеки, или работают на уровне raw sockets).[^1]
- Теоретически можно усилить через WFP (Windows Filtering Platform) и перенаправление трафика, но это сложная кастомизация, хрупкая при обновлениях и перезагрузках.[^1]
- Эмпирическая проверка сложнее: нужно гарантировать, что каждое приложение не обойдёт прокси; при падении прокси — заблокировать весь интернет, что требует глубокой интеграции с файрволом и политик маршрутов.[^1]


### DNS

- Прокси часто не перехватывает DNS; приложения резолвят имена локально, отправляя UDP/53 напрямую — утечка DNS высока.[^1]
- Можно форсировать DoH/DoT на уровне ОС, но это отдельный механизм, не гарантирующий привязку к прокси‑пути.[^1]


### IPv4/IPv6

- Прокси обычно IPv4‑ориентирован; IPv6‑трафик может обойти прокси, если не заблокирован на уровне файрвола/маршрутов.[^1]
- При появлении глобального IPv6 в новой сети риск обхода возрастает.[^1]


### Независимость приложений

- Git/SSH/терминальные утилиты могут не использовать системный прокси без явной конфигурации; это нарушает принцип «без настройки на приложение».[^1]


### Операционная сложность

- Высокая: требуется централизованная политика прокси, контроль за обходами, дополнительные механизмы для DNS и IPv6, кастомные правила WFP.[^1]
- Диагностика сложнее из‑за разнородного поведения приложений.[^1]


## 5. Оверлей‑сети (например, mesh/overlay поверх обычного транспорта)

### Граница безопасности

Оверлей создаёт логическую сеть поверх физической, но сам по себе не отменяет прямой маршрут по умолчанию на физическом интерфейсе.[^1]

### Fail‑closed

- Без дополнительных мер (маршруты/файрвол) трафик по‑прежнему может уходить напрямую в интернет.[^1]
- Оверлей обычно оптимизирован для связности между узлами, а не для блокировки всего остального трафика.[^1]


### DNS/IPv6/Маршрутизация

- DNS остаётся на усмотрение ОС/приложений; оверлей не гарантирует его перехват или шифрование.[^1]
- IPv6 может обойти оверлей, если не заблокирован.[^1]
- Маршруты оверлея сосуществуют с обычными маршрутами; нужен внешний механизм для принудительного туннелирования.[^1]


### Независимость приложений

- Приложения, не использующие оверлей, идут напрямую; требуется дополнительная инфраструктура для принуждения трафика.[^1]


### Операционная сложность

- Для цели RU‑001 (fail‑closed для всего интернета) оверлей сам по себе недостаточен; потребуется комбинация с VPN/файрволом, что усложняет архитектуру.[^1]


## 6. Анализ режимов отказа (кратко, по ключевым сценариям)

1. Туннель недоступен при загрузке: при правильной политике — интернет заблокирован; при ошибочной — восстановится прямой дефолт (опасно).[^1]
2. Разрыв туннеля после работы: трафик должен остановиться; если клиент восстановит маршрут через физический интерфейс — утечка.[^1]
3. Ошибка аутентификации: туннель не поднимается — интернет заблокирован (при корректной политике).[^1]
4–5. DNS‑сбой/недоступность резолвера: резольвинг падает; важно не откатываться к публичным DNS.[^1]
6–8. Смена сети/шлюза: клиент должен пересобирать туннель и сохранять политику «дефолт только через туннель».[^1]
4. Появление IPv6: без явной блокировки/туннелирования — возможный обход.[^1]
10–12. Старт приложения до туннеля/ребут/сон‑пробуждение: критично, чтобы политика маршрутов применялась до разрешения трафика.[^1]
13–15. Падение сервиса/повреждение конфига: должны срабатывать безопасные состояния (блокировка), а не откат к прямому интернету.[^1]

## 7. DNS: детальный разбор для Windows

- Windows использует интерфейс‑зависимые DNS‑серверы; при нескольких активных интерфейсах приоритеты и метрики влияют на выбор.[^1]
- При подъёме туннеля необходимо: заменить системные DNS на резолверы туннеля, запретить исходящий UDP/53 к внешним IP (кроме endpoint‑ов), и отключить автоматический откат к DHCP‑DNS физического интерфейса.[^1]
- При разрыве туннеля: DNS‑запросы должны перестать уходить; если ОС подставит резервные DNS физического интерфейса — это утечка.[^1]
- Для усиления: форсировать DoH/DoT на уровне ОС, но только как дополнение к маршрутной политике, а не замену.[^1]


## 8. IPv4/IPv6: раздельная оценка

- IPv4: управляем через маршрут по умолчанию; kill‑switch реализуем.[^1]
- IPv6: сегодня глобального IPv6 нет, но архитектура должна предполагать его появление в другой сети; требуется явная политика (отключить или туннелировать + kill‑switch для ::/0).  Без этого возможен обход.[^1]


## 9. Мобильность (смена сетей)

- Дом/офис/публичная сеть/хотспот: клиент должен переподнимать туннель и восстанавливать политику маршрутов/DNS.[^1]
- Сети с разным DNS: системные DNS должны переключаться на туннельные, игнорируя локальные.[^1]
- Сети с IPv6: требуется блокировка/туннелирование IPv6, иначе обход.[^1]


## 10. implications для будущего Compute Node

- Системный VPN даёт чистую точку расширения: можно организовать отдельный туннель/сегмент между EMS‑001 и Compute Node, сохраняя общую политику fail‑closed.[^1]
- Прокси/оверлей усложняют создание единого безопасного канала без дополнительных механизмов.[^1]

## 12. Адверсариальная критика предпочтительного решения (системный VPN)

Сильнейший аргумент против: в реальной Windows‑среде «kill‑switch» часто реализуруется клиентом VPN на уровне приложения, а не на уровне ОС, и может не устоять при сбое клиента, обновлении драйверов, или изменении политик DHCP/IPv6.  Если клиент по какой‑то причине восстановит маршрут по умолчанию через физический интерфейс при разрыве туннеля, произойдёт тихая утечка всего трафика.  Кроме того, DNS‑поведение Windows (резервные серверы, Smart Multi‑Homed Resolution) может создать обходной путь, даже если маршрут по умолчанию заблокирован.[^1]

Вывод: предпочтительная архитектура требует независимой верификации на уровне ОС (маршруты, файрвол, DNS), а не доверия к логике клиента.[^1]

## 13. Итоговая рекомендация

1. Предпочтительный класс: системный VPN с принудительным туннелированием и kill‑switch на уровне маршрутов/файрвола.[^1]
2. Второй вариант: прокси‑архитектура только как дополнение для конкретных приложений, но не как основной механизм fail‑closed.[^1]
3. Отклонённый вариант: оверлей‑сеть сама по себе — не удовлетворяет требованию fail‑closed для всего трафика.[^1]
4. Почему: только системный VPN даёт единый слой ниже приложений, управляемый маршрут по умолчанию и возможность блокировки прямого выхода.[^1]
5. Когда не выбирать VPN: если невозможно гарантировать, что клиент не восстановит прямой маршрут при сбое, или если требуется строгая независимость от сторонней инфраструктуры без возможности верификации.[^1]
6. Что проверить на EMS‑001 до внедрения: поведение таблицы маршрутов при подъёме/падении туннеля, DNS‑утечки при разрыве, реакцию на появление IPv6, восстановление после ребута/сна, работу при смене сети.[^1]

## 14. План экспериментальной верификации (на EMS‑001)

- Сценарии: загрузка без туннеля, разрыв туннеля во время трафика, смена сети, принудительное появление IPv6 (если возможно), отключение DNS туннеля.[^1]
- Метрики: наличие/отсутствие 0.0.0.0/0 и ::/0 на физическом интерфейсе, результаты внешних HTTPS‑запросов, DNS‑запросы к публичным резолверам, логи файрвола.[^1]
- Критерий успеха: при отсутствии туннеля — весь интернет‑трафик заблокирован; DNS не уходит к публичным резолверам; при появлении IPv6 — обхода нет.[^1]
