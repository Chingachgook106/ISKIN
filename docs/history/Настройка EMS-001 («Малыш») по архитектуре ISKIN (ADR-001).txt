Зажми выбранную комбинацию (или кнопку `Fn + Tab`, если на ней есть значок Bluetooth) примерно на 3 секунды [[38], [39]]. Индикатор на клавиатуре должен начать быстро мигать (обычно синим цветом) — это значит, что она готова к сопряжению и видна для ПК .

Чтобы тачпад и горячие клавиши работали корректно именно в среде Windows, клавиатуру нужно перевести в соответствующий режим. Обычно за это отвечает комбинация `Fn + W` (или клавиша с логотипом Windows) [[41], [43]].

**Шаг 4. Подключение в Windows 11 Pro**
1. На мини-ПК открой **Параметры** (Win + I) и перейди в раздел **Bluetooth и устройства**.
2. Убедись, что Bluetooth включен, и нажми кнопку **Добавление устройства** -> **Bluetooth**.
3. В списке доступных устройств найди свою клавиатуру (она может называться «Bluetooth Keyboard», «iBOX 11», «Foldable Keyboard» или просто «Keyboard»).

## Шаг 10.2. Проверка TCP-порта RDP

Теперь нужно проверить, действительно ли EMS-001 слушает TCP-порт RDP.  
Статус службы `Running` ещё не гарантирует, что сетевой слушатель работает.

Выполни на EMS-001 в PowerShell от администратора:

```powershell
$rdpPort = (Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp' -Name PortNumber -ErrorAction SilentlyContinue).PortNumber

if (-not $rdpPort) {
    $rdpPort = 3389
}

"Configured RDP port: $rdpPort"

Get-NetTCPConnection -LocalPort $rdpPort -State Listen -ErrorAction SilentlyContinue |
ForEach-Object {
    $proc = Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue

    [pscustomobject]@{
        LocalAddress  = $_.LocalAddress
        LocalPort     = $_.LocalPort
        State         = $_.State
        OwningProcess = $_.OwningProcess
        ProcessName   = $proc.ProcessName
    }
}
```

---

### Что проверяет эта команда

1. Какой порт настроен для RDP.
2. Есть ли активный TCP-слушатель на этом порту.
3. Какой процесс владеет слушателем.

---

### Нормальный результат

Примерно такой:

```text
Configured RDP port: 3389

LocalAddress LocalPort State  OwningProcess ProcessName

0.0.0.0      3389      Listen 1234          svchost
```

или похожая строка со `State = Listen`.

Это означает, что EMS-001 реально принимает входящие TCP-соединения на RDP-порт.

## Про галочку Remote Assistance

Вот эта вещь:

```text

```

или по-русски:

```text

```

**не является главным переключателем RDP**.

Remote Assistance — это отдельный механизм помощи/сеанса с приглашением.  
Для обычного административного RDP-доступа главный параметр — именно:

```text
Allow remote connections to this computer
```

Так что галочка Remote Assistance сама по себе проблему не объясняет.

## Про NLA

Вот эта строка:

```text
Allow connections only from computers running Remote Desktop with Network Level Authentication (recommended)
```

или по-русски:

```text
Разрешить подключения только с компьютеров, на которых запущен удалённый рабочий стол с проверкой подлинности на уровне сети
```

сейчас у тебя **не включена**.

### Влияет ли она на текущую проблему?

Прямо сейчас — **нет, не выглядит первопричиной**.

Причина простая:

- у нас вообще нет TCP-слушателя RDP;
- порт 3389 не слушается;
- `qwinsta` не показывает `rdp-tcp`.

А NLA относится к этапу проверки подлинности уже после того, как клиент дошёл до RDP-сервера.

То есть NLA может влиять на ошибки аутентификации, на отказ при установке сеанса, на совместимость клиента и сервера, но она не должна приводить к тому, что в системе полностью отсутствует RDP-слушатель.

### Менять ли её сейчас?

Нет, сейчас не меняем.

Фиксируем текущее состояние:

```text
NLA: не требуется / галочка снята
```

Позже, когда RDP заработает, мы отдельно решим, возвращать ли более безопасный режим с NLA. По ТЗ просто так отключать или включать NLA без причины нельзя.

## Что теперь нужно проверить

Раз интерфейс говорит, что Remote Desktop разрешён, но слушателя нет, нужно проверить фактическое системное состояние в реестре.

Начнём с главного флага запрета RDP.

### Команда 1

Выполни:

```cmd

```

Нажми `Enter`.

### Что проверяем

Фактический системный параметр, который запрещает или разрешает Remote Desktop.

### Норма



Это тоже нормально.

```text

```

И это будет очень вероятная первоначальная причина, почему интерфейс может показывать одно, а слушатель не создаётся.

## Следующий диагностический шаг: контролируемый перезапуск TermService

Мы сейчас не меняем ни реестр, ни политики, ни Firewall, ни NLA.

Мы делаем диагностический перезапуск службы, чтобы проверить, не находится ли служба в зависшем состоянии, когда конфигурация уже разрешает RDP, но слушатель не создан.

### Почему это обосновано

Потому что:

- служба запущена;
- системный запрет отсутствует;
- политика не обнаружена;
- интерфейс показывает разрешение;
- но слушателя нет.

Перезапуск службы — это минимальное воздействие, которое может заставить Windows перечитать состояние и создать RDP-слушатель.

На всякий случай сохрани открытую работу на EMS-001.

Активного RDP-сеанса у нас нет, но мы перезапускаем службу, связанную с удалёнными сеансами, поэтому сохранить работу — разумная инженерная предосторожность.

## Интерпретация

Служба приняла команду остановки (появился `STOP_PENDING`), но остановку не завершила и вернулась в `RUNNING`.

Это ожидаемое поведение для `TermService`: он управляет всеми терминальными сеансами системы, включая твою локальную консольную сессию `indeez` (мы видели её как `Active` в `qwinsta`). Пока пользователь залогинен, служба не может полностью освободить сеансы, поэтому остановка откатывается обратно в `RUNNING`.

То есть:

- это не ошибка ввода команд;
- это не проблема прав (ты в `Administrator: Command Prompt`, видно по заголовку окна);
- это значит, что эксперимент «перезапуск службы» в залогиненном состоянии выполнить нельзя.

Вывод: чистая переинициализация `TermService` возможна только через перезагрузку. И это даже в тему — по ТЗ устойчивость после перезагрузки всё равно входит в критерий завершения.

**Но перезагружаем пока не сейчас.** У нас всё ещё открыт старый диагностический вопрос: самая первая проверка `PortNumber` в разделе `RDP-Tcp` закончилась ошибкой. Если конфигурация WinStation повреждена или отсутствует, перезагрузка ничего не исправит, а мы потратим цикл вслепую.

## Следующий шаг: полная проверка WinStation RDP-Tcp

`[ADMIN]` — не обязательно (чтение реестра), но ты уже в админской консоли, так что выполняй там же.

Команда:

```cmd
reg query "HKLM\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp"
```

### Что проверяем

- существует ли вообще раздел WinStation `RDP-Tcp`;
- какие параметры в нём лежат (`PortNumber`, `fEnableWinStation`, `SecurityLayer`, `UserAuthentication` и т.д.).

### Норма

Длинный список значений. Нас в нём интересуют в первую очередь:

```text
PortNumber    REG_DWORD    0xd3d
fEnableWinStation    REG_DWORD    0x1
```

(`0xd3d` — это 3389 в шестнадцатеричном виде.)

### Отклонения

- Ошибка `unable to find the specified registry key or value` → раздел или его содержимое отсутствуют. Это уже серьёзная заявка на первопричину: службе не из чего создавать слушатель.
- `fEnableWinStation = 0x0` → подключение отключено на уровне WinStation, слушатель создаваться не будет.
- `PortNumber` отсутствует или отличается от `0xd3d` → неверная конфигурация порта.

### Нужно ли менять

Сейчас — нет. Сначала фиксируем фактическое состояние. Вывод будет длинным — просто сфотографируй его целиком.

## Параллельная короткая проверка

## Почему это критично

В исправной Windows в этом разделе лежит вся конфигурация RDP-слушателя. Там normalmente должны быть значения вроде:

- `PortNumber` (0xd3d = 3389);
- `fEnableWinStation` (0x1);
- `SecurityLayer`;
- `UserAuthentication`;
- `MinEncryptionLevel`;
- и ряд других.

Точный список мы сейчас подтвердим сравнением, а не по памяти.

Если раздел пуст, то всё сходится в одну картину:

- службе не на каком порту слушать → отсюда самая первая ошибка запроса `PortNumber`;
- WinStation считается отключённой, потому что нет `fEnableWinStation`;
- `TermService` работает, но слушатель не создаётся → отсюда пустой `netstat` и отсутствие `rdp-tcp` в `qwinsta`;

## Заявка на изменение (по правилу 12 ТЗ)

**Почему:** раздел `RDP-Tcp` на EMS-001 пуст → WinStation не имеет конфигурации транспорта и порта → TermService не создаёт слушатель (подтверждено: `netstat` пуст, `qwinsta` без `rdp-tcp`).

**Что:** импорт штатного набора значений `RDP-Tcp` (скопирован с эталонной машины той же семьи ОС) через проверенный `.reg`-файл. Никаких других изменений (Firewall, службы, политики) не делаем.

**Зачем:** вернуть TermService корректную конфигурацию WinStation, чтобы появился TCP-слушатель 3389 и заработал RDP.

**Проверка:** после импорта и перезагрузки — `qwinsta` показывает `rdp-tcp Listen`; `netstat -ano | findstr :3389` показывает `LISTENING`; затем успешное RDP-подключение с основного ПК.

### Что включено и что исключено (документирую)

- Включены все непустые значения эталона: транспорт (`PdDLL=tdtcp`, `PdName=tcp`, `WdName`, `LoadableProtocol_Object`, `SelectTransport`), порт (`PortNumber=0xd3d`), включение WinStation (`fEnableWinStation=1`), безопасность (`SecurityLayer=2`, `MinEncryptionLevel=2`, `UserAuthentication=1`) и штатные параметры сеансов.
- Исключены пустые `REG_SZ` (`Username`, `Password`, `Domain`, `Comment` и т.п.) — их отсутствие эквивалентно пустой строке.
- Исключены подразделы `TSMMRemotingAllowedApps` и `VideoRemotingWindowNames` — к созданию слушателя и базовому подключению отношения не имеют; при потребности вернём отдельным шагом.

### Решение по NLA (осознанное, фиксирую)

Эталон содержит `UserAuthentication=1` (NLA требуется). После импорта галочка NLA на «Малыше» станет включённой — это изменение относительно зафиксированного исходного состояния («не требуется»), и я его обосновываю:

- это штатное, рекомендованное и более безопасное состояние;
- клиент (основной ПК, Windows 11) полностью поддерживает NLA, подключению это не помешает;
- ТЗ запрещает именно отключать NLA без основания, а мы возвращаем стандартную безопасную конфигурацию.

Если захочешь сохранить прежний режим «NLA не требуется» — это один документированный DWORD (`UserAuthentication=0`), сделаем отдельным решением. Я рекомендую оставить `1`.

## 2. Диагностическая последовательность

1. **Служба (10.1):** `TermService` — `Running`, `StartType Manual`. Служба жива; `Manual` для неё допустим.
2. **TCP-порт (10.2):** `reg query ...RDP-Tcp /v PortNumber` → ошибка «value not found»; `netstat -ano | findstr <PID TermService>` → пусто; `qwinsta` → нет строки `rdp-tcp Listen`; `netstat -ano | findstr :3389` → пусто. **Вывод: служба запущена, но RDP-слушатель отсутствует.**
3. **Контролируемый перезапуск службы:** `sc stop TermService` → `STOP_PENDING` → возврат в `RUNNING`. Служба не останавливается при активной пользовательской сессии; переинициализация на месте невозможна, требуется перезагрузка.
4. **Параметры RDP (10.4):** `fDenyTSConnections = 0x0`; в `SystemPropertiesRemote.exe` — «разрешить подключения»; запрещающей политики в `HKLM\SOFTWARE\Policies\...\Terminal Services` не обнаружено. **Конфигурация «разрешает», но слушателя нет.**
5. **NLA (10.5):** исходно «не требуется» (галочка снята). Зафиксировано; не отключалось.
6. **WinStation RDP-Tcp:** раздел существует, но содержит только `(Default)` — конфигурация транспорта/порта отсутствует.
7. **Сравнение с эталоном:** на основном ПК тот же раздел содержит полный штатный набор значений.

## 3. Точная точка отказа RDP

Пустой раздел реестра:

```text

```

Без `PortNumber`, `fEnableWinStation` и определений транспорта (`PdDLL/PdName/WdName/...`) TermService не создаёт слушатель.

Конфигурация WinStation `RDP-Tcp` на EMS-001 отсутствовала/опустошена. **Почему она опустела — не установлено достоверно**; версии (действия предыдущего инженера/твикера, системный сбой) зафиксированы как гипотезы, не как факты.

## Способ 1. Перенаправление дисков через RDP — доступно прямо сейчас, ноль изменений

RDP умеет «пробрасывать» локальные диски основного ПК внутрь удалённого сеанса. Это отдельный канал (RDPDR), он не зависит от той односторонности буфера обмена, с которой мы столкнулись.

`[USER]`, на основном ПК:

1. Запусти `mstsc` (или открой свойства сохранённого `.rdp`-ярлыка).
2. Нажми **«Показать параметры»**.
3. Вкладка **«Локальные ресурсы»** → в блоке «Локальные устройства и ресурсы» нажми **«Подробнее…»**.
4. Раскрой **«Диски»** и отметь галочкой нужный диск (или все).
5. Нажми ОК и **«Подключиться»**.

Внутри сеанса на «Малыше»: Проводник → **«Этот компьютер»** → в разделе «Перенаправленные диски и папки» появятся диски большого ПК. Копируешь в любую сторону обычным drag-and-drop:

- с перенаправленного диска на рабочий стол «Малыша» — передача **большой ПК → EMS-001**;
- с «Малыша» на перенаправленный диск — передача **EMS-001 → большой ПК**.

**Плюсы:** никаких изменений конфигурации, обе стороны, работает по уже настроенному административному каналу.
**Минусы:** требует активной RDP-сессии; это «ручной» административный способ, а не машинный.

По ТЗ это легитимно: RDP — административный канал, а перенос файлов администратором — административная задача. Но строить вокруг этого экспериментальный контур мы, разумеется, не будем.

## Шаг 2. Сделать доступ воспроизводимым (заявка на изменение, клиентская)

(`/pass` попросит ввести пароль; он сохранится в Credential Manager Большого ПК, защищён твоим входом в систему — для доверенного стенда это штатная практика.)

### 1. Про "Том без метки"
Когда ты вводишь команду `dir` для сетевой папки, Windows выдаёт стандартную шапку:

Это **не означает**, что мы как-то разделили физический диск Малыша, отформатировали его или сломали файловую систему. Это просто стандартный текст, который выдаёт консоль для любого сетевого ресурса (SMB-шары), у которого нет "человеческого" имени тома (как, например, «Локальный диск (C:)» или «Data (D:)»). 

Для SMB-шар это абсолютно нормальный и ожидаемый вывод. Все твои файлы физически лежат на обычном диске `C:` Малыша, в папке `C:\iskin-exchange`. Мы не вносили никаких изменений в структуру его дисков.

### ASSISTANT
Манни, если интерфейс отдаёт оба варианта — моя инженерная рекомендация такая:

**JSON — как архивный первоисточник (source of truth).**
- Сохраняет структуру: роли, порядок и границы сообщений, вложения, метаданные.
- Машинно-читаем: в будущем скрипты ISKIN смогут вытащить из него команды, отчёты, CR-блоки — это ровно та философия оркестрации, которую мы строим.
- Главный аргумент: из JSON ты всегда сгенерируешь читабельный текст, а вот из .txt структуру обратно **не восстановишь** — это потеряное преобразование.

**.txt (а лучше .md) — как человекочитаемая копия.**
- Для быстрого чтения тобой и ГлавАрхитектором без конвертеров.
- .md предпочтительнее: заголовки и код-блоки красиво отрендерятся в VS Code и на GitHub.

### Итог

Места текст занимает копейки, поэтому бери **оба**: JSON в `journal/` (или `evidence/`) как первоисточник, рядом `.md` как читабельная версия. Если придётся выбрать только один — бери **JSON**.
