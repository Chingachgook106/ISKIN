# ADR-001 — Четырёхслойная архитектура ISKIN и роль EMS-001

**Статус:** Accepted
**Дата:** 2026-08-08
**Проект:** ISKIN
**Архитектурный узел:** EMS-001 («Малыш»)

---

## 1. Контекст

ISKIN является инженерно-исследовательским проектом, в котором вычислительная инфраструктура является инструментом проведения воспроизводимых экспериментов.

Основным принципом является отделение исследовательской задачи от конкретной вычислительной машины. Инфраструктура должна обеспечивать воспроизводимость, контроль условий эксперимента, документирование, независимую проверку и сохранение истории решений.

В ходе архитектурного анализа внешней оценки взаимодействия мини-ПК и вычислительного ПК с GPU выявлена необходимость явного разделения:

* управляющего узла;
* вычислительного узла;
* исследовательского уровня;
* базовой инфраструктуры.

Принято решение использовать EMS-001 («Малыш») как управляющий и оркестрационный узел ISKIN, а вычислительные задачи, требующие дискретного GPU, выполнять на отдельном Compute Node.

При этом архитектура должна быть реализуема на **минимальной аппаратной конфигурации EMS-001, имеющейся на момент принятия данного ADR**.

Будущее увеличение оперативной памяти EMS-001 допускается и не должно требовать изменения базовой архитектуры.

---

## 2. Архитектурное решение

ISKIN организуется как четырёхслойная система.

```text
┌──────────────────────────────────────────────┐
│               RESEARCH LAYER                 │
│                                              │
│ гипотезы • эксперименты • анализ • выводы   │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│            ORCHESTRATION LAYER               │
│                                              │
│             EMS-001 / «Малыш»               │
│                                              │
│ планирование • запуск • контроль • журнал   │
└──────────────────────┬───────────────────────┘
                       │
                 API / SSH / jobs
                       │
┌──────────────────────▼───────────────────────┐
│               COMPUTE LAYER                  │
│                                              │
│ GPU Node • LLM • inference • training       │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│            INFRASTRUCTURE LAYER              │
│                                              │
│ hardware • OS • network • storage            │
└──────────────────────────────────────────────┘
```

Эти уровни являются **логическими архитектурными границами**, а не обязательным требованием размещать каждый уровень на отдельном физическом компьютере.

---

## 3. EMS-001 («Малыш»)

EMS-001 получает роль:

> **Control / Orchestration Node ISKIN**

Основные функции EMS-001:

* управление вычислительными задачами;
* оркестрация взаимодействия между узлами;
* запуск и контроль экспериментов;
* сбор результатов и журналов;
* хранение и управление конфигурациями;
* работа с Git-репозиторием ISKIN;
* инженерная документация;
* независимая разработка и редактирование программного кода;
* административное управление вычислительными узлами;
* самостоятельная работа как переносного инженерного компьютера.

EMS-001 **не обязан обладать производительностью Compute Node**.

Отсутствие мощного дискретного GPU на EMS-001 не является архитектурным недостатком.

---

## 4. Независимая инженерная функция EMS-001

EMS-001 не является исключительно терминалом доступа к Compute Node.

Он должен оставаться самостоятельным рабочим узлом, способным выполнять локальные инженерные задачи независимо от наличия вычислительного сервера.

В состав базовой программной среды EMS-001 входит:

* Git;
* **Visual Studio Code (VS Code)**;
* необходимые средства работы с исходным кодом;
* средства работы с конфигурационными файлами;
* терминальные инструменты;
* средства сетевого и системного администрирования.

VS Code является штатным компонентом архитектуры EMS-001.

Его назначение:

* написание кода;
* редактирование кода;
* ревизия существующего кода;
* работа с конфигурациями;
* локальная разработка;
* подготовка и обслуживание инструментов ISKIN.

Работа в VS Code на EMS-001 не должна зависеть от подключения к Compute Node.

---

## 5. Compute Node

Компьютер с дискретным GPU рассматривается как:

> **Compute Node ISKIN**

Его основная функция — выполнение вычислительных задач, требующих соответствующих вычислительных ресурсов.

На Compute Node могут выполняться:

* локальные LLM;
* inference;
* обучение и дообучение моделей;
* CUDA/GPU-вычисления;
* иные ресурсоёмкие задачи ISKIN.

Compute Node не является обязательным местом хранения архитектурного состояния проекта.

По возможности вычислительный узел должен выполнять полученную задачу, а управление экспериментом и его фиксация должны оставаться в управляющем контуре EMS-001.

---

## 6. Машинное взаимодействие EMS-001 ↔ Compute Node

Основным архитектурным принципом является:

> **управление вычислением не должно зависеть от удалённого рабочего стола.**

Для машинного взаимодействия предусматривается сервисный контур:

```text
EMS-001
   │
   ├── command
   ├── configuration
   ├── job
   │
   ▼
Compute Node
   │
   ├── execution
   ├── logs
   ├── metrics
   └── results
   │
   ▼
EMS-001
```

Конкретная реализация транспортного механизма может быть определена позднее.

В качестве базовых средств допускается использование SSH, API и иных машинных интерфейсов, не требующих интерактивной графической сессии.

---

## 7. RDP и удалённый графический доступ

RDP рассматривается как **административный и пользовательский канал**, а не как обязательная часть экспериментального контура.

RDP может использоваться для:

* настройки Compute Node;
* диагностики;
* запуска графических приложений;
* визуального контроля;
* обслуживания Windows-среды.

Эксперимент ISKIN не должен становиться неработоспособным вследствие отсутствия активной RDP-сессии.

Специализированные решения высокопроизводительного удалённого графического доступа, включая NICE DCV / PCoIP и аналогичные технологии, **не являются обязательными компонентами текущей архитектуры**.

Их внедрение возможно в будущем при возникновении подтверждённой потребности.

---

## 8. Сетевая архитектура

Основным способом связи между узлами считается проводное Ethernet-соединение.

Целевой принцип:

```text
             LAN / SWITCH
             ┌─────┴─────┐
             │           │
        EMS-001       Compute Node
```

Сетевая архитектура должна позволять добавлять дополнительные узлы без изменения роли EMS-001.

Прямое соединение EMS-001 ↔ Compute Node допустимо как инженерная конфигурация стенда, но не фиксируется как единственный архитектурный вариант.

Wi-Fi не запрещается для вспомогательных задач, однако не рассматривается как предпочтительный основной канал вычислительного контура.

---

## 9. Аппаратная база EMS-001

Базовая архитектура EMS-001 должна быть реализуема на **минимальной аппаратной конфигурации, фактически установленной на момент принятия ADR-001**.

Архитектура не должна исходить из предполагаемых будущих модернизаций.

Это означает:

> **сначала проектируется система, работающая на существующем «Малыше», затем допускается увеличение её ресурсов без изменения архитектурных границ.**

---

## 10. Расширение оперативной памяти

Увеличение RAM EMS-001 в будущем допускается.

Ожидаемое возможное увеличение — вплоть до удвоения текущего объёма, ориентировочно в течение ближайших нескольких месяцев.

Это изменение считается:

> **capacity upgrade, а не architectural change.**

Увеличение RAM:

* не меняет роль EMS-001;
* не меняет его принадлежность к Orchestration Layer;
* не превращает его в Compute Node;
* не требует изменения сетевой архитектуры;
* не требует изменения программных архитектурных границ.

После увеличения RAM дополнительный ресурс может использоваться для:

* более тяжёлых локальных инструментов;
* дополнительных сервисов оркестрации;
* локальных моделей меньшего размера;
* более сложной разработки;
* дополнительных контейнеров/сервисов при необходимости.

При этом программное окружение должно сохранять работоспособность на исходной минимальной конфигурации.

---

## 11. Принцип минимальной конфигурации

Минимальная текущая конфигурация EMS-001 является **нормативной базовой точкой проекта**.

Все дополнительные ресурсы рассматриваются как:

```text
Base configuration
        +
optional capacity
```

а не:

```text
new hardware
        =
new architecture
```

Таким образом, ISKIN не должен приобретать архитектурную зависимость от будущего апгрейда EMS-001.

---

## 12. Архитектурная масштабируемость

Архитектура EMS-001 должна допускать расширение вычислительного контура:

```text
                    EMS-001
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
      Compute A    Compute B    Compute C
```

На начальном этапе может существовать только один Compute Node.

Наличие одного вычислительного узла не должно приводить к архитектурной привязке EMS-001 непосредственно к этому конкретному компьютеру.

---

## 13. Принцип разделения ролей

Фиксируются следующие роли:

| Компонент            | Роль                                     |
| -------------------- | ---------------------------------------- |
| ISKIN Research Layer | исследовательская задача и интерпретация |
| EMS-001              | управление и оркестрация                 |
| Compute Node         | вычисление                               |
| Infrastructure Layer | физическая и системная среда             |
| VS Code на EMS-001   | независимая разработка и редактирование  |
| RDP                  | административный графический доступ      |
| SSH/API              | машинное взаимодействие                  |

---

## 14. Что сознательно НЕ фиксируется этим ADR

ADR-001 не определяет:

* конкретную модель GPU;
* конкретную будущую модель Compute Node;
* конкретный объём будущей RAM EMS-001;
* конкретную ОС будущих узлов;
* конкретный orchestration framework;
* конкретный API-протокол;
* обязательность Docker/Podman/виртуальных машин;
* обязательность NICE DCV/PCoIP;
* окончательную схему хранения больших исследовательских данных.

Эти вопросы должны решаться отдельными ADR или инженерными решениями после появления соответствующей потребности.

---

## 15. Архитектурный инвариант

Следующее положение считается основным инвариантом ADR-001:

> **EMS-001 является независимым управляющим и инженерным узлом ISKIN, а вычислительная мощность является внешним расширяемым ресурсом, подключаемым к нему через машинный интерфейс.**

При этом EMS-001 должен сохранять способность работать самостоятельно на своей минимальной текущей аппаратной конфигурации.

---

## 16. Обоснование решения

Решение принято по следующим причинам:

1. Разделяет управление экспериментом и его исполнение.
2. Снижает зависимость исследовательского контура от конкретного GPU-компьютера.
3. Позволяет в будущем добавлять вычислительные узлы.
4. Сохраняет EMS-001 полезным даже при отключённом Compute Node.
5. Не требует преждевременного усложнения инфраструктуры.
6. Позволяет использовать текущий минимальный hardware baseline.
7. Допускает увеличение RAM без архитектурного пересмотра.
8. Делает VS Code и локальную разработку штатной функцией EMS-001.
9. Отделяет административный графический доступ от машинного экспериментального интерфейса.
10. Соответствует принципам воспроизводимости и контроля условий, принятым в ISKIN.

---

## 17. Следствие для дальнейшей настройки EMS-001

После принятия ADR-001 настройка «Малыша» должна выполняться не как произвольная установка набора программ, а как **реализация утверждённой архитектурной роли Control / Orchestration Node**.

Первый этап настройки должен обеспечить минимальный автономный набор:

```text
EMS-001
│
├── OS
├── Git
├── VS Code
├── Terminal / shell
├── базовые средства разработки
├── базовые средства администрирования
└── сетевой доступ к Compute Node
```

После этого добавляются только те компоненты оркестрации и экспериментального контура, необходимость которых будет подтверждена следующими инженерными решениями.

---

## 18. Статус решения

**ACCEPTED**

ADR-001 является базовым архитектурным решением для последующей настройки EMS-001 и построения вычислительного контура ISKIN.

Изменение четырёхслойной модели или роли EMS-001 требует отдельного архитектурного решения.

Увеличение аппаратных ресурсов EMS-001 в пределах сохранения его роли не считается изменением архитектуры.
