# ТЗ: компонентная база LLM и ПО Малыша для ISKIN

**Статус:** базовая реализация
**Архитектура:** Client–Server / API
**Inference:** Большой ПК
**Субъект / управляющая среда:** Малыш
**Distributed inference:** **ОТКАЗАТЬСЯ от реализации на данном этапе**

                  │  ISKIN Core     │

### Принцип

**Малыш является клиентом. Большой ПК является вычислительным сервером.**

Малыш:

* формирует запрос;
* формирует контекст;
* управляет экспериментом;
* хранит состояние;
* получает результат;
* анализирует результат.

Большой ПК:

* загружает модель;
* выполняет inference;
* возвращает результат через API.

**Большой ПК не является вторым экземпляром ISKIN.**

# 2. Модель

Зафиксировать:

> **OLMo 3 7B Instruct**

Не использовать:

* OLMo 3 7B Base;
* OLMo 3 7B Think.

Для inference используется GGUF:

> **`Olmo-3-7B-Instruct-Q4_K_M.gguf`**

Указанный инженерами источник:

[Рекомендованный источник GGUF](https://cloudcodetree.com/ai-news/2026-08-10-01-gguf-quantization-ollama-levels/?utm_source=chatgpt.com)

При этом перед установкой инженер должен **проверить целостность файла и соответствие модели OLMo 3 7B Instruct**, а не принимать имя файла как достаточное подтверждение происхождения.

`Q4_K_M` выбран как компромисс между качеством, размером модели и требованиями к VRAM.

# 3. Большой ПК — Compute Server

Аппаратная конфигурация:

* AMD Ryzen 3 3200G;
* 4 ядра / 4 потока;
* 32 GB RAM;
* NVIDIA GeForce RTX 4060;
* 8 GB dedicated VRAM;
* Windows;
* 100 Mbps Ethernet;
* 100 GB свободно на SSD C:;
* 931 GB свободно на HDD D:.

### Назначение

Большой ПК используется **только как вычислительный узел inference**.

Не требуется превращать его в полноценную development environment ISKIN.

---

# 4. Inference runtime

## Основной выбор

> **llama.cpp / llama-server**

Не устанавливать одновременно для baseline:

* Ollama;
* LM Studio;
* vLLM;
* другие inference servers.

Причина — воспроизводимость и контроль конфигурации.

`llama-server` является HTTP-сервером с OpenAI-compatible API; официальная документация llama.cpp показывает запуск сервера и endpoint `/v1/chat/completions`. Проект также имеет CUDA backend для NVIDIA и поддерживает CPU+GPU hybrid inference. ([GitHub][1])

### Требование

Выбрать **готовую Windows CUDA-сборку llama.cpp**, если доступна подходящая стабильная сборка.

Не собирать llama.cpp из исходников без необходимости.

Цель первого этапа:

> минимальное количество самостоятельно собираемых компонентов.

---

# 5. CUDA

CUDA относится **только к Большому ПК**.

### На Большом ПК:

* NVIDIA driver — уже установлен;
* установить/использовать CUDA runtime, необходимый выбранной CUDA-сборке llama.cpp;
* проверить обнаружение RTX 4060;
* проверить фактический GPU offload.

### На Малыше:

**CUDA НЕ устанавливать.**

Также не устанавливать на Малыше:

* CUDA Toolkit;
* NVIDIA CUDA runtime;
* CUDA-enabled PyTorch;
* llama.cpp для локального inference;
* Ollama;
* LM Studio.

Это принципиальное архитектурное требование.

---

# 6. Размещение модели

Модель должна находиться **на Большом ПК**.

Предпочтительно:

```text
D:\AI\Models\OLMo-3-7B-Instruct-Q4_K_M.gguf
```

или аналогичный каталог, согласованный инженером.

Почему D:, а не C::

* C: имеет только 100 GB свободного места;
* D: имеет 931 GB;
* модельные файлы и будущие экспериментальные checkpoints лучше не смешивать с системным диском.

Каталог должен иметь понятное разделение:

```text
D:\AI\
    Models\
    Runtime\
    Logs\
    Benchmarks\
```

Конкретную структуру инженер может изменить, если она сохраняет эту логическую организацию.

# 7. API между Малышом и Большим ПК

Здесь **не фиксируем конкретный API implementation** — это оставляем инженеру.

Но архитектурный принцип обязателен:

> **между ISKIN и inference server должна существовать стабильная абстракция API, не зависящая от конкретного inference runtime.**

То есть ISKIN не должен знать, что на Большом ПК используется именно llama.cpp.

Сегодня:

```text
ISKIN → llama.cpp
```

завтра теоретически:

```text
ISKIN → другой inference server
```

без переписывания ISKIN Core.

---

## Минимальный API contract

Инженер должен предусмотреть как минимум логические операции:

```text
HEALTH
MODEL INFO
CHAT / COMPLETION
```

Желательно ориентироваться на OpenAI-compatible структуру.

Для llama-server такой API уже предусмотрен официально. ([GitHub][1])

### Особое требование

**Health check должен быть отделён от inference.**

ISKIN должен уметь определить:

```
Большой ПК доступен
        +
Inference server доступен
        +
Модель загружена
```

до отправки исследовательского запроса.

---

# 8. Сетевой принцип

Использовать существующую локальную Ethernet-сеть.

```
Малыш
   │
   │ Ethernet
   ▼
Router
   │
   │ Ethernet
   ▼
Большой ПК
```

RDP остаётся каналом администрирования.

**Не использовать RDP как транспорт inference.**

Inference должен идти непосредственно по TCP/HTTP между клиентом и API-сервером.

---

# 9. Безопасность API

Поскольку API предназначен для локальной сети:

### Требуется

* сервер должен слушать **только LAN-интерфейс**, необходимый для Малыша;
* не публиковать inference API в Интернет;
* не делать port forwarding на роутере;
* не открывать API наружу;
* разрешить соединения Windows Firewall только от Малыша либо из соответствующего LAN-сегмента.

Если инженер считает необходимым добавить authentication — это допустимо.

Но:

> **API не должен зависеть от внешнего authentication service.**

Система должна работать автономно после Isolation.

# 10. Context window

### Первый baseline

> **4096 tokens**

Не начинать сразу с 8K.

После успешной стабилизации:

```
4096
 ↓
8192
```

и сравнить:

* VRAM;
* RAM;
* prompt processing;
* token generation;
* стабильность;
* latency.

Официальная документация llama.cpp позволяет задавать размер контекста через `-c/--ctx-size`. ([GitHub][1])

### 6–8K

Рассматривать **как экспериментальный режим**, а не как baseline.

---

# 11. GPU offload

Первоначальная цель:

> **максимально возможный GPU offload модели при сохранении стабильности RTX 4060 8 GB.**

Не задавать инженеру произвольное значение `n_gpu_layers` заранее.

Порядок:

1. загрузить модель;
2. определить доступную VRAM;
3. выполнить максимальный разумный offload;
4. проверить отсутствие OOM;
5. зафиксировать фактический параметр;
6. сравнить с CPU/hybrid fallback при необходимости.

Это важнее теоретического утверждения, что файл модели «меньше 8 GB».

---

# 12. CPU threads

Здесь исправляем рекомендацию стороннего эксперта.

Большой ПК имеет:

> **4 logical processors.**

Поэтому `8–12 CPU threads` для него невозможны.

### Начальный benchmark

> **4 CPU threads**

Затем инженер может проверить:

```
2
3
4
```

и выбрать оптимум.

Не требуется искусственно использовать все доступные CPU-ресурсы.

Главный вычислительный ресурс Большого ПК:

> **RTX 4060.**

## Набор тестов

### Test A — загрузка

Проверить:

* модель загружается;
* API поднимается;
* GPU определяется;
* нет OOM;
* нет crash.

---

### Test B — короткий prompt

Например:

```
Explain in three sentences what a feedback loop is.
```

Измерить:

* время до первого токена;
* tokens/sec;
* полное время ответа.

---

### Test C — средний prompt

Около 500–1000 input tokens.

Измерить:

* prompt processing;
* generation;
* total latency;
* RAM;
* VRAM.

---

### Test D — контекст 4096

Заполнить значительную часть контекста.

Проверить:

* стабильность;
* VRAM;
* RAM;
* скорость;
* корректность ответа.

---

### Test E — API

Запрос должен пройти:

```
Малыш
  ↓
HTTP
  ↓
llama-server
  ↓
OLMo
  ↓
HTTP
  ↓
Малыш
```

и результат должен быть получен программой на Малыше.

Это **обязательная часть benchmark**, потому что нас интересует не standalone inference, а именно наша Client–Server архитектура.

# 18. Исследовательская копия OLMo

На Малыше сохраняется возможность **исследовать архитектуру OLMo**, но это отдельная задача от штатного inference.

Поэтому инженер должен разделять:

```
MODEL INFERENCE
```

и

```
MODEL RESEARCH
```

Inference:

> Большой ПК → GGUF → RTX 4060.

Research:

> Малыш → Python/PyTorch/Transformers → исследование архитектуры.

Не нужно пытаться заставить исследовательский checkpoint 7B работать на 16 GB RAM Малыша в качестве штатного inference.

## 25. Главный архитектурный принцип проекта

Я бы добавил его в самое начало ТЗ:

> **Малыш не является терминалом удалённой LLM. Малыш является субъектом, использующим LLM как внешний вычислительный ресурс.**

Это важное различие.

LLM не управляет Малышом через API.

Направление взаимодействия:

```
ISKIN
  │
  │ формирует запрос
  ▼
LLM
  │
  │ возвращает вычисленный результат
  ▼
ISKIN
```

Решение о том, **что делать с результатом**, остаётся на стороне Малыша.
