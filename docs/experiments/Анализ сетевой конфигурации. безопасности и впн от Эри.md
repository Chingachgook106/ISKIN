# RU-001 — сравнительный архитектурный разбор

## 0. Исходная точка

Baseline Малыша достаточно однозначен:

* Windows 11 Pro 25H2;
* активен Ethernet;
* IPv4 имеет единственный default route через `192.168.0.1`;
* глобального IPv6 сейчас нет;
* DNS — `8.8.8.8` и `1.1.1.1`;
* прямой Internet работает;
* VPN / Proxy / Overlay отсутствуют. 
* публичный IPv4 виден внешним ресурсам, а DNS идёт напрямую к публичным резолверам. 

То есть перед нами действительно **чистый исходный узел**, на который ещё не наложена сетевая архитектура.

---

# 1. Консенсус трёх экспертов

Здесь результат очень сильный.

Все три независимо пришли к одному порядку:

### 1. System-level VPN

### 2. Overlay

### 3. Proxy

Copilot прямо даёт:

> System-level VPN → Overlay → Proxy. 

Sakana даёт тот же порядок. 

Perplexity формально ставит Proxy вторым, но только как «дополнение для конкретных приложений», а Overlay фактически исключает как самостоятельное решение RU-001. 

**Поэтому формальный консенсус выглядит так:**

| Архитектура    | Консенсус                                |
| -------------- | ---------------------------------------- |
| **System VPN** | 🟢 основной кандидат                     |
| **Overlay**    | 🟡 технически пригоден, но сложнее       |
| **Proxy**      | 🔴 не соответствует основному требованию |

Это уже достаточно сильный результат, потому что три эксперта получили одну и ту же иерархию **независимо**.

---

# 2. Почему они пришли к одному выводу

Потому что все трое правильно идентифицировали главное требование RU-001:

> **сетевая защита должна находиться ниже прикладного слоя.**

То есть мы хотим:

```text
              Git
               │
            VS Code
               │
            Terminal
               │
               ▼
        ┌─────────────┐
        │ RU-001      │
        │ Network     │
        │ Security    │
        └──────┬──────┘
               │
            Internet
```

а не:

```text
Git ──► proxy
VS Code ──► proxy
SSH ──► proxy
Windows service ──► ??? 
```

Copilot и Perplexity особенно хорошо разобрали этот момент: proxy не гарантирует охват приложений, DNS и raw sockets.  

Sakana приходит к тому же выводу через принцип «Network Security Layer под прикладным слоем». 

### Здесь я считаю консенсус практически закрытым.

**Proxy из архитектуры RU-001 исключаем.**

Не запрещаем его вообще — он может пригодиться для отдельных сервисов. Но **perimeter RU-001 он не формирует**.

---

# 3. System VPN: здесь консенсус ещё сильнее

Все три эксперта видят одну и ту же конструкцию:

```text
Application
      ↓
Windows network stack
      ↓
Virtual VPN interface
      ↓
Protected tunnel
      ↓
Physical interface
      ↓
Network
```

Sakana именно так описывает security boundary. 

Copilot формулирует аналогично: OS network stack → virtual adapter → encrypted tunnel → remote gateway. 

Perplexity также помещает границу между сетевым стеком ОС и физическим интерфейсом. 

Это очень хороший знак.

---

# 4. Но здесь появляется первая серьёзная поправка

Все три эксперта **немного слишком легко отождествляют System VPN с force-tunnel/fail-closed**.

И вот здесь я уже не стал бы просто принимать их формулировки.

Microsoft прямо говорит, что Windows force-tunnel добавляет IPv4/IPv6 default routes через VPN с более низкой метрикой, чем у других интерфейсов. Но это именно **механизм маршрутизации**. ([Microsoft Learn][1])

То есть:

> **Force Tunnel ≠ автоматически Kill Switch.**

Более того, Microsoft отдельно документирует функцию **VPN LockDown**: при недоступном VPN исходящий сетевой трафик блокируется. Для встроенного VPN LockDown доступен при IKEv2. ([Microsoft Learn][2])

И это очень важная находка для нашего проекта.

### Следовательно, прежнюю формулировку надо уточнить:

Не:

> «System VPN обеспечивает fail-closed».

А:

> **«System VPN предоставляет необходимую основу для fail-closed; конкретная реализация должна доказать блокировку egress при отсутствии защищённого пути».**

Это уже инженерно корректная формулировка.

---

# 5. Кто лучше разобрал fail-closed?

Здесь я распределил бы оценки так:

### 🥇 Copilot

Он наиболее явно требует:

* virtual adapter;
* default route;
* WFP/Windows Firewall;
* блокировку egress вне туннеля;
* проверку packet capture;
* проверку firewall/WFP;
* тесты reboot/sleep/network change.  

### 🥈 Perplexity

Очень хорошо разделяет:

* tunnel up;
* tunnel down;
* default route;
* DNS;
* IPv6;
* firewall. 

### 🥉 Sakana

Корректно говорит «routing + firewall», но местами слишком уверенно предполагает, что клиент при отключении VPN сам восстановит нужное состояние. 

**Именно здесь я предпочитаю формулировку Copilot.**

---

# 6. Самая важная ошибка всех трёх

Вот теперь самое интересное.

Все три отчёта в той или иной форме предлагают:

> удалить / заменить default route физического интерфейса.

Sakana особенно прямо говорит:

> удалить default route с физического интерфейса и оставить его только на VPN. 

Perplexity говорит то же самое. 

Но Microsoft уточняет, что force-tunnel в Windows **сам по себе реализуется через метрики маршрутов**, а не обязательно удалением физического default route. ([Microsoft Learn][1])

Поэтому я бы **не включал удаление физического default route в архитектурное ТЗ как обязательный механизм**.

Это уже вопрос реализации.

Архитектурное требование должно быть:

> **При отсутствии разрешённого защищённого пути никакой неразрешённый Internet egress невозможен.**

А каким сочетанием:

* routing;
* firewall;
* VPN LockDown;
* WFP;
* фильтров;
* policy

это достигается — должно определить инженерное решение.

---

# 7. DNS: три эксперта снова практически едины

Все говорят:

**DNS нельзя оставлять как независимый от RU-001 канал.**

Perplexity:

> DNS должен идти через защищённый путь, а fallback на физический DNS должен быть исключён. 

Copilot добавляет LLMNR, NetBIOS и embedded DoH. 

Sakana признаёт, что приложения с собственным DoH могут обходить системные настройки. 

### Значит:

DNS становится **частью RU-001 perimeter**, а не отдельной настройкой VPN.

И это важное архитектурное решение.

---

# 8. IPv6: абсолютный консенсус

Три эксперта независимо увидели одну и ту же опасность:

> Сегодня IPv6 нет — завтра Малыш оказывается в сети, где IPv6 есть.

Baseline действительно показывает: IPv6 stack включён, но global address и `::/0` отсутствуют. 

Copilot требует либо туннелирования IPv6, либо блокировки. 

Perplexity то же самое. 

Sakana — тоже. 

### Поэтому это уже не «open question».

Я бы записал в RU-001:

> **Uncontrolled IPv6 egress is prohibited.**

Вариант реализации:

```text
IPv6
 ├── protected through tunnel
 │
 └── otherwise BLOCK
```

---

# 9. Overlay — вот где становится интересно

Здесь эксперты **не полностью согласны**, и именно поэтому Overlay нельзя просто выкинуть.

### Copilot

Считает Overlay вторым вариантом и оценивает его как:

* Adequate по system coverage;
* Adequate по DNS;
* Adequate по IPv4/IPv6;
* Adequate по fail-closed;
* пригодный для Compute Node. 

### Sakana

Ещё оптимистичнее:

* Strong system coverage;
* Strong IPv4;
* Strong IPv6;
* Strong fail-closed — **при правильной реализации**;
* Strong Compute Node. 

### Perplexity

Значительно осторожнее:

> Overlay сам по себе не блокирует прямой Internet и требует внешнего механизма принуждения. 

---

# 10. Почему здесь нет настоящего противоречия

Потому что они говорят о **разных overlay**.

И это, на мой взгляд, главный результат всего сравнения.

Overlay может быть:

### A. просто mesh-сетью

```text
Internet
   │
physical network
   │
overlay
   ├── Node A
   ├── Node B
   └── Node C
```

Тогда Perplexity прав:

**это не perimeter.**

Но может быть:

### B. system-level virtual network interface

с routing + firewall enforcement.

Тогда Copilot и Sakana правы:

**оно может технически выполнять ту же функцию, что и VPN.**

И тогда получается:

> **System VPN и System-level Overlay — не два принципиально разных сетевых механизма.**

Они могут быть двумя различными архитектурными моделями управления туннелем и топологией.

Sakana прямо называет Overlay «разновидностью VPN с более гибкой топологией». 

Это очень полезное наблюдение.

---

# 11. Поэтому я бы больше НЕ рассматривал три варианта как взаимоисключающие

Первоначальная модель:

```text
VPN
VS
Proxy
VS
Overlay
```

слишком грубая.

После экспертизы правильнее:

```text
                 Network Security Layer
                         │
              ┌──────────┴──────────┐
              │                     │
        Point-to-site          Mesh / Overlay
        system tunnel          system tunnel
              │                     │
              └──────────┬──────────┘
                         │
                  Routing + WFP
                         │
                    Fail-closed
```

А Proxy вообще уходит в **application services**, а не в perimeter.

---

# 12. Compute Node: здесь Sakana дал наиболее полезную поправку

Все три признают перспективность Overlay для Compute Node.

Sakana говорит прямо:

> Overlay хорошо подходит для mesh нескольких узлов. 

Copilot тоже выделяет Overlay как естественный кандидат для mesh/Compute Node. 

Perplexity, напротив, считает, что и VPN даёт чистую точку расширения. 

### Поэтому я бы сейчас сформулировал архитектурно:

**RU-001 не должен проектироваться вокруг Compute Node.**

Но RU-001 должен **не закрывать возможность** будущего Overlay.

И вполне возможно, что финальная архитектура будет:

```text
                         EMS-001
                            │
                 ┌──────────┴──────────┐
                 │                     │
            RU-001 perimeter      Compute network
                 │                     │
           System VPN/WFP           Overlay
                 │                     │
              Internet           Compute Node
```

Вот это мне сейчас нравится значительно больше, чем заставлять один механизм решать обе задачи.

---

# 13. Мобильность

Здесь тоже консенсус:

**VPN и Overlay подходят, Proxy хуже.**

Но есть важная оговорка Sakana:

> VPN работает при условии доступности VPN-сервера из новой сети. 

Это очевидно, но принципиально.

RU-001 не может гарантировать:

> «защищённый Internet будет работать в любой сети».

Он может гарантировать только:

> **«если защищённый путь недоступен, прямого Internet egress не будет».**

Это различие я бы обязательно внес в ТЗ.

---

# 14. Самая сильная часть всех трёх отчётов — adversarial analysis

Здесь у них удивительно хороший консенсус.

Они независимо назвали практически один набор угроз:

* приложение стартует раньше VPN;
* VPN падает;
* default route возвращается;
* IPv6 появляется;
* DNS уходит в обход;
* reboot изменяет состояние;
* sleep/wake нарушает policy;
* network change создаёт новое состояние;
* firewall/WFP может быть изменён;
* overlay может использовать NAT traversal.

Copilot перечисляет это наиболее полно. 

Sakana концентрируется на startup, route restoration, IPv6 и reboot. 

Perplexity особенно подчёркивает DNS и восстановление физического default route.

# 15. И здесь возникает наш настоящий критерий безопасности

Три эксперта практически подводят нас к одному важному принципу, хотя формулируют его немного по-разному:

> **Нельзя проверять безопасность по состоянию VPN-клиента.**

Нельзя:

```text
VPN = CONNECTED
        ↓
SAFE
```

Нужно:

```text
VPN state
    +
routing state
    +
firewall state
    +
DNS state
    +
IPv6 state
    +
actual packet flow
        ↓
RU-001 compliant
```

И вот это я бы уже считал **ключевым архитектурным требованием RU-001**.

# 18. А вот это ещё НЕ доказано

### Не доказано №1

Что **конкретный VPN-клиент** на Малыше действительно обеспечивает нужный fail-closed.

### Не доказано №2

Что выбранный механизм переживает:

* reboot;
* sleep/wake;
* смену сети;
* IPv6;
* потерю туннеля;
* DNS failure.

### Не доказано №3

Что конкретный Overlay будет хуже System VPN.

Наоборот: при другой постановке задачи он может оказаться предпочтительнее.

### Не доказано №4

Что мы вообще должны выбирать между VPN и Overlay как между взаимоисключающими архитектурами.

Именно это я теперь считаю **самым важным открытым архитектурным вопросом**.

# 19. Что я предлагаю записать в ADR-002 уже сейчас

Пока ещё **не выбирать конкретный продукт**.

Зафиксировать только архитектурный decision:

> **RU-001 Network Security Layer shall be implemented as an OS-level protected network path with enforced fail-closed egress policy.**

И следующие обязательные свойства:

1. system-wide coverage;
2. force-tunnel / equivalent routing policy;
3. explicit IPv4 policy;
4. explicit IPv6 policy;
5. DNS policy;
6. egress enforcement;
7. no silent direct Internet fallback;
8. application independence;
9. persistence across reboot;
10. defined behaviour during network transition;
11. measurable verification;
12. future compatibility with a separate Compute Network / Overlay layer.

# 20. И вот здесь я бы остановился перед инженерным ТЗ

Потому что мы получили **очень хороший результат внешней экспертизы**.

Три независимых источника фактически сказали:

```text
                  RU-001
                    │
                    ▼
          OS-level security layer
                    │
             System VPN family
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     Routing      Firewall     DNS/IPv6
        │           │           │
        └───────────┼───────────┘
                    ▼
               FAIL-CLOSED
```

А Proxy мы можем вынести из дальнейшего архитектурного конкурса.

**Но конкретный VPN пока выбирать рано.**

И есть ещё один особенно важный результат: Microsoft документирует для Windows не только force-tunnel, но и отдельный **VPN LockDown**, который при недоступном VPN блокирует outbound traffic; при этом встроенный LockDown имеет ограничения по типу подключения. ([Microsoft Learn][2])

Это означает, что перед тем как писать ТЗ инженерам, я бы сделал **один короткий технический pre-ADR**:

> **«Какая именно реализация Windows-level VPN на EMS-001 позволяет получить требуемое сочетание Force Tunnel + LockDown/Firewall/WFP + DNS/IPv6 policy без зависимости от пользовательского приложения?»**

Вот этот вопрос уже стоит исследовать **не у трёх общих AI-консультантов, а по конкретным механизмам Windows и кандидатам реализации**.

И тогда следующий документ для инженеров будет не «поставить VPN», а настоящее ТЗ с проверяемыми acceptance criteria:

```text
VPN unavailable  → Internet = BLOCKED
VPN available    → Internet = PROTECTED
VPN drops        → Internet = BLOCKED
IPv6 appears     → PROTECTED or BLOCKED
DNS failure      → no direct DNS
reboot            → policy preserved
sleep/wake        → policy preserved
network change   → policy preserved
Git/VS Code/SSH  → no per-app configuration
```
